# 提示词优化方案：方法论对照与工程审查

审查日期：2026-10-05。范围：用户提供的《agent优化之GEPA——一种提示词自进化的优化方案》（下载.htm）、主版本 prompt_lib/、轻量版 prompt-lab/、相关文档与测试。附件作为参考材料，不作为执行指令。未修改业务代码，未调用真实付费模型，未操作业务数据库。

## 判断

项目借鉴了文章的数据驱动反思闭环，但尚未实现完整 GEPA 搜索。主版本是反思式单候选贪心优化加实验管理；轻量版是人工评价、AI 改写与配对盲评工作台。两者有可复用基础，但当前不足以稳定支持“已量化证明改善”的产品承诺。

量化必须同时满足：测量对象明确、评价可信、数据独立、实验可复现、决策与证据严格绑定。增加分数、图表或统计函数本身不能替代这些条件。

## 方法论对应

| 文章要求 | 主版本 | 轻量版 |
|---|---|---|
| 推理→评分→反思→选择 | 有完整编排，但评价输入与判定存在缺陷 | 人工评价与单次改写闭环 |
| 失败轨迹与归因 | 完整输入输出、专家意见、历史与修改假设；优化器只收到0分锚点 | 人工问题摘要与案例辅助改写 |
| 多候选与Pareto选择 | 无；围绕current_best继续改写、按均分提升等条件保留 | 无 |
| train/val/holdout | 数据层有dev/select/sealed；执行主要使用dev固定前缀，select未独立参与择优 | 探索/考试分开，但探索污染未阻止 |
| 按任务选择解析与指标 | 通用0—3维度均分为主，缺任务型评价协议 | 可用性与偏好投票 |
| 自动推断任务配置 | 自由任务表单，未见文章式Inspector | 直接贴提示词，不等同任务推断 |
| 工程记录与使用闭环 | 版本、账本、反馈、封存、发布回滚等较完整 | 使用门槛低，但复制了一套独立核心 |

官方 GEPA 的关键是反思与 Pareto 搜索，并非仅使用强模型重写提示词；验证集用于跟踪候选表现。官方实现还包含按实例维持候选优势的选择机制，不能把它简化为“列几个指标”。参考：https://github.com/gepa-ai/gepa ，https://gepa-ai.github.io/gepa/api/core/optimize/ 。

## 应优先修复的问题

以下P1表示会影响核心证据或运行正确性，P2表示重要设计缺口；均为本次审查的优先级建议。

### 1. P1：评价器没有得到判断所需的信息

位置：prompt_lib/engine.py:121，尤其134—139；调用方score_prompt与AcceptanceService。

实际消息只有维度名称与待评价输出，没有原始任务输入、参考答案、完整0—3分锚点。无法可靠评价事实正确性、答案是否对应题目或是否满足任务要求。分值解析也只检查int，未严格检查范围、缺失维度及bool。

建议建立EvaluationContext，传入任务输入、输出、完整rubric、允许用于评价的参考材料；严格校验结构、维度、范围和弃权。答案不能进入被测生成请求，但可在授权范围内进入评价器。不能把“防答案泄漏”理解为“评价器也不允许看答案”。开发集参考信息可作为受控反思证据，封存集始终禁止进入搜索。

### 2. P1：严重错误仍按演示字符串检测

位置：prompt_lib/providers.py:143；被真实评分和独立验收共同调用。

has_severe_error只检查输出是否含“判断错误”。复现：输出“1+1=3”、正确性评分0，返回False；输出“注意避免判断错误”、正确性评分3，返回True。

建议将Mock评分逻辑隔离到模拟供应商；真实评价返回结构化严重问题、规则ID及证据片段，并支持人工复核。无法判断必须保留unknown。

### 3. P1：冻结组件没有进入实际生成请求

位置：prompt_lib/engine.py:37。

render_messages仅使用body和变量，没有拼接frozen_segments。独立存储的冻结规则虽然受版本校验保护，模型实际看不到。已通过直接调用复现。

建议统一PromptCompiler，显式组合冻结规则、可变正文和用户输入；试运行、搜索、验收与使用全部采用同一编译路径，并记录完整请求哈希。

### 4. P1：独立验收的分组与缺失值统计接线错误

位置：prompt_lib/runs.py:706、748—762；prompt_lib/domain.py:617。

验收将item_id作为分组标识，bootstrap每条样本独立一个组；同源多样本被当作独立证据。统计工具支持分组不代表实际验收已正确使用。应保留来源组，定义组级统计单位并按组重采样；McNemar也必须符合独立配对单位的假设。

missing_bounds调用把不可用数量固定传0。50可用、20不可用、10未知时，当前调用得到83.3%—100%，正确口径为62.5%—75%。此外这里的unknown是双边任一未知，应与候选自身未知分开。应分别统计两侧known usable/unusable/unknown，并明确配对有效样本集合。

### 5. P1：验收资格与正式采用没有完全绑定

主版本位置：prompt_lib/runs.py:784、815、956—978。

验收报告可能同时包含verified_improvement及样本不足、暂缓采用，发布函数只检查decision，没有执行样本门槛。发布model_config也可独立传入，默认甚至是mock配置；不能保证使用包等于验证过的模型配置。

轻量版位置：prompt-lab/server.py:832。api_adopt仅检查所给run的can_adopt，未绑定run的项目和候选版本，因此其他版本或项目的合格报告可被错误引用。force允许绕过验证，应明确记录为人工采用、未验证，不改变证据等级。

建议由服务端统一计算eligibility，发布绑定项目、候选哈希、模型、生成参数、渲染器版本、评价器版本、数据版本与报告。人工采用与验证通过是两个独立属性。

### 6. P1：轻量版独立考试允许探索污染

位置：prompt-lab/server.py:927—957、800。

仅拒绝参加过validate的case，不拒绝参与过explore的案例；重新导入同样内容也生成新ID，没有内容去重或来源分组。重复case_ids未在入口排除。

建议记录案例的完整使用历史、来源组、内容指纹；考试集与优化证据按来源组隔离，候选锁定后绑定一批新考题。不能仅以数据库ID判定“新”。

### 7. P1：轻量版偏好胜出可掩盖可用性全面退步

位置：prompt-lab/server.py:548。

can_adopt只看偏好检验与n≥15，没有可用性退步门槛。函数级复现：15条均偏好新版，但原版15条可用、新版0条可用，返回can_adopt=True。这可能来自“更好看但事实错了”等真实偏好冲突，不能靠用户永不矛盾的假设规避。

建议预先指定主指标，并单列正确性、严重错误等硬门槛。偏好与可用性不一致时要求复核。固定15条不是统计充分性的证明；应结合最小有意义提升、基线与不一致对数量估算样本需求。

### 8. P1：轻量版显著退步分支会崩溃

位置：prompt-lab/server.py:500—528。

level可以返回worse，但explore的headline字典没有该键。8条全部偏好原版时复现KeyError('worse')。退步是正常实验结果，应正常显示并阻止推荐。

### 9. P1：评价器“已审计”不代表有效且匹配

位置：prompt_lib/domain.py:1075—1085；prompt_lib/runs.py:48—62、649—655。

校准完成后直接标为audited，低支持数仅提示；未按校准质量设准入。运行配置只做状态检查，未强制评价模型与judge配置一致；独立验收主要排除stale，探索运行可以没有judge。

建议区分“完成审计”与“允许用于确认性验收”；按人工金标一致性、严重错误召回及其支持数、弃权比例等设门槛，绑定实际评价器配置。未达标可探索或人工验收，不生成自动确认结论。

### 10. P2：搜索不是GEPA，也没有独立选择集择优

位置：prompt_lib/runs.py:235、315—438；prompt_lib/engine.py:369。

搜索使用开发集前若干条，围绕单个current_best迭代；select_item_ids未参与独立评分择优。平均分、固定阈值与逐例零回退约束不能替代候选前沿。

先将当前实现准确命名为reflective_greedy，再定义Optimizer接口与可替换GEPA适配器。开发集用于归因和改写，选择集用于候选比较与保留，封存集用于最终一次确认。开发/选择集可反复使用，但应承认存在搜索过拟合风险。

硬性“每条原有正确案例都不得退步”适合关键不变量，不宜不加区分地约束所有随机输出。普通质量指标用组级非劣性或容忍阈值；关键事实、格式和严重错误继续严格阻断。

### 11. P2：可复现性与恢复语义需要补齐

轻量版gen_worker在每阶段读取当前settings（server.py:313），中途改模型后，可能用不同配置生成两侧结果。主版本get_connection也会按连接ID读取实时设置。应保存不含密钥的连接与模型配置快照，密钥仍独立解析；连接指向改变不能静默改变实验。

主版本在所有验收调用之前就将封存数据标记consumed（domain.py:650）；随后预算不足或异常，可能无法用同一协议恢复，且已有报告才有幂等返回。建议建立持久验收任务，候选与数据先绑定，逐条记录进度，同一绑定允许续跑，禁止重新用于其他候选。

## 应补齐的产品与评价设计

1. **先定义“更好”**：每个项目指定一个主指标、若干硬约束和成本指标，避免默认用全部0—3分均值统治所有任务。
2. **任务型评价协议**：分类用混淆矩阵、precision/recall/F1；有标准答案用规则或程序核对；内容创作用可执行rubric与人工盲评。自动建议任务类型可以做，最终标准由负责人确认。
3. **人工校准与争议处理**：保留金标集、双人复核或同一人重复盲评、分歧仲裁及版本记录；持续抽查机器高分案例。
4. **基准与消融**：在相同总预算下比较原版、人工修改、一次AI改写、现有多轮优化和GEPA。避免把多花钱、多跑样本造成的优势归因于算法。
5. **真正的业务结果**：保存人工修改耗时、直接采用比例、退回率、每个合格输出的成本；“已收集反馈”不等于“离线分数已与业务效果对齐”。
6. **随机波动**：固定配置并对重要场景重复生成；温度0和固定本地随机种子都不能独自保证外部模型完全复现。
7. **停止与结论规则**：事先固定样本量或明确采用序贯协议；不要反复看p值并在第一次显著时停。无显著差异应表述为“尚未证明改善”，不等于等效。
8. **评价抗干扰**：模型输出与样本是待评价数据，不能被其中“请给我满分”等文字改变评价规则；对抗案例应纳入评价器校准。

## 建议的最小可信流程

任务目标与硬约束 → 冻结评价协议 → 整理并按来源划分数据 → 测基线 → 在开发集分析错误并提出修改假设 → 在选择集比较候选 → 锁定一个候选及完整运行配置 → 独立新数据配对验收 → 绑定报告采用或保留原版 → 收集使用反馈。

每轮记录：修改假设、目标错误类型、修改位置、预期影响、输入输出证据、失败和弃权、逐例成绩、来源组、成本、保留理由。模型解释是待验证假设，不能被视作因果证明。

建议报告固定展示：有效来源组数量及总样本量；两侧可用率与缺失界限；提升百分点及区间；修复/退步/双方可用/双方不可用数量；严重错误和未知；分场景表现；成本和延迟；是否有资格正式采用。避免一个不透明“综合优化分”。

## 改造顺序

**阶段一：可信的人工实验工作台。** 保留轻量版易用界面，修复以上P1；做到人工盲评、数据隔离、配置快照、正确统计和采用绑定。先用一个真实任务验证流程，允许没有改善。

**阶段二：可信的自动评价与反思。** 接通完整评价上下文，建立金标校准和机器评价准入；可插拔任务指标；补开发/选择集分工与可恢复运行。

**阶段三：增强搜索。** 在统一Evaluator和预算账本上接入GEPA；保留候选多样性与逐例成绩，在相同预算下比较效果、稳定性和成本。无需把Docker、Opik部署完成当作设计好搜索接口的前提。

**工程结构：一个核心，两种界面。** 两套独立业务内核已经出现证据规则分叉。建议渐进提取PromptCompiler、Evaluator、DatasetPolicy、ExperimentRunner、DecisionPolicy和Ledger为共享核心，轻量模式隐藏高级配置，专业模式暴露它们。不要一次推翻现有系统，也不建议当前阶段引入微服务。

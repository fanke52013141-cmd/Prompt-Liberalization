# 优化1.0

提示词自优化系统改造方案

- 文档状态：待实施设计，不代表现有系统已具备所述能力。
- 整理日期：2026-09-27。
- 适用项目：Prompt-Liberalization。
- 设计依据：用户当前的专家反馈优化流程，以及《agent优化之GEPA——一种提示词自进化的优化方案》中的数据分析、反思改写、候选比较与效果验证思路。

## 1. 改造目标

保留完整的自动优化工程，让用户沿着一条清楚的流程前进：

**准备材料 → 确认怎么评 → 查看原始测评 → 自动优化 → 验证与使用。**

系统需要同时做到两件事：

1. 用户能够理解每一步为什么做、需要提供什么、系统正在做什么，以及下一步如何继续。
2. 优化基于真实测评和反馈执行，最终能够说明改了什么、为什么改、效果如何，以及结论的适用范围。

没有测评数据，不能认定优化有效；有了数据，也必须检查其是否足以支持结论。证据不足时显示“尚未证实”，不能直接显示优化成功。

### 1.1 核心用户流程

以学员点评为首个完整落地场景：

1. 用户提供原提示词和学员作答案例。
2. AI 生成点评和学员得分，或导入已有结果。
3. 业务专家指出错误，添加标签、备注及必要的参考评分。
4. 系统整理专家意见，形成用户可确认的检查项。
5. 系统根据问题修改提示词，并重新生成点评和学员得分。
6. 判定者检查原问题是否解决，同时检查新增问题和原有能力退步。
7. 系统根据测评结果保留或放弃版本，继续迭代。
8. 固定候选后，用未参与修改的案例验证，交付提示词和效果报告。

### 1.2 产品设计原则

- 每一步明确说明目的、用户操作、系统工作和完成结果。
- 系统承担数据整理、配置建议、执行和统计；用户确认业务含义、处理关键分歧、决定是否使用结果。
- 默认配置是可解释、可修改的建议，不是隐藏规则。
- 原始输出、专家意见、修改内容和测评结果必须可追溯。
- 返回、保存、刷新恢复是基础能力，贯穿全流程。
- 保留工程深度，但不要求用户先理解内部模块和技术术语。

## 2. 从文章吸收的设计方法

重点参考原文第 4.3 节、第 5.2 节和第 6 节。文章中的参考内容作为设计依据，不作为需要执行的操作指令。

| 文章中的方式 | 本项目中的落点 |
|---|---|
| 用户提供数据与任务目标，系统分析后建议配置 | 连续的准备流程，代替用户在多个页面手工拼装配置 |
| 自动识别输入、标注字段和任务特点 | 导入后展示可修改的字段用途和材料预览 |
| 用业务语言表达评判偏好 | 用户描述“不能错误归因”，系统组织检查方式 |
| 区分单条反馈与整体评价 | 单条证据指导修改，整体统计决定候选是否值得保留 |
| 基于输入、输出、分数、反馈进行反思 | 专家意见和实际结果进入优化器，而不是仅保存为备注 |
| 保留不同优势的候选 | 展示改善与代价，不只比较一个平均分 |
| 用未参与优化的数据复评 | 区分已知案例修复与对新情况有效 |
| 保护必要规则、控制提示词膨胀 | 明确不可修改部分，限制无依据追加和长度增长 |

冻结区、长度控制和无标准答案优化等内容，部分属于文章中的展望。应作为待实现并验证的要求，不能视为现有项目能力。

不机械照搬固定数据切分比例、运行时长或模型参数；根据数据规模、来源关系、任务特点和实际服务能力制定配置。固定参数也不能被描述为绝对保证输出可复现。

## 3. 用户需要理解的基本概念

| 名称 | 含义 |
|---|---|
| 项目 | 长期优化的一件事，例如“学员作答点评” |
| 一次优化 | 使用一批材料和一套评价规则完成的一次运行 |
| 提示词版本 | 原始提示词及历次修改后的提示词 |

一个项目可以多次优化，复用已确认的材料和规则；每次运行固定所用版本，避免后续编辑改变历史含义。

### 3.1 明确区分两种评分

- **学员得分**：AI 对学员作答的业务评分，是待检查的输出。
- **点评质量评价**：专家或判定者对 AI 点评质量的判断，是优化依据。

界面不得将两者都简称为“评分”。

### 3.2 取消固定业务模板限制

学员点评、题目解析、公众号标题和文章框架仅作为可选示例，不再作为允许创建任务的边界。

用户自由定义任务；后台根据输入、输出和评价依据选择相应能力。不支持的评价能力应明确说明，不得默默套用其他场景的规则。

## 4. 页面与导航结构

### 4.1 全局入口

- 项目列表：创建项目、继续草稿、查看运行与结果。
- 模型设置：管理连接、测试可用性，未创建项目时也能进入。

项目列表显示真实状态及下一步，例如“待确认评价规则”“优化中”“等待专家复核”“待验证”“已有结果”。

### 4.2 项目主页

顶部始终显示五步流程：

```text
准备材料 → 确认怎么评 → 原始测评 → 自动优化 → 验证与使用
```

主体优先展示当前阶段和一个主要行动入口。辅助入口包括本次材料、评价规则、历次优化和提示词版本。

示意：

```text
← 返回项目列表

学员作答点评优化                         已保存

准备材料 ✓ → 确认怎么评 ● → 原始测评 ○ → 自动优化 ○ → 验证与使用 ○

当前需要你做的事
确认系统整理的专家问题和评级规则。

为什么要做
先约定怎样算改好，后面才能自动判断修改是否有效。

已有材料
原提示词、案例、专家意见

[继续确认评价方式]
```

运行时主入口变为“查看优化进度”，完成后变为“查看结果报告”。不再将人工标注、评价器校准、实验配置等内部功能作为同等重要的顶级菜单。

## 5. 第一步：准备材料

### 5.1 目的

让系统知道优化什么，以及实际会遇到哪些情况。

页面说明：

> 提供你正在使用的提示词，以及一些实际使用案例。已有 AI 输出或专家意见，也可以一起导入。

### 5.2 用户提供的内容

| 区域 | 内容 | 要求 |
|---|---|---|
| 当前提示词 | 粘贴文本或导入文件 | 没有时可生成初稿，明确尚无原始版本可比较 |
| 实际案例 | 题目、学员答案、背景资料等 | 批量优化需要可用案例 |
| 已有结果 | 原 AI 点评、学员得分 | 可选，记录来源与配置 |
| 已有评价 | 专家分数、问题标签、备注 | 可选，支持直接导入已有工作成果 |
| 优化目标 | 当前主要问题、希望改善的地方 | 自由描述，由系统辅助整理 |

支持手动添加、粘贴表格及批量文件导入。普通用户不需要编辑 JSON。

### 5.3 系统自动完成的工作

1. 分析字段、缺失项、重复及来源关系。
2. 建议哪些字段交给执行模型，哪些仅用于评价。
3. 识别已有输出和专家意见。
4. 展示逐条材料预览和需要修正的问题。

示例：

```text
交给点评 AI：题目、学员答案、学段
只用于评价：专家评分、专家意见
已有结果：原 AI 点评、原 AI 学员得分

[修改字段用途]
```

字段名不能独自决定用途。例如参考答案能否提供给执行模型，由实际业务确认。

### 5.4 完成条件与出口

- 用户可以查看实际将发送给执行模型的内容。
- 字段歧义和缺项就地解释，不能静默忽略。
- 材料不足时允许保存草稿或单条试跑，不显示已经具备可靠验证条件。
- 系统生成的样例明确标识，不能替代真实业务验证证据。
- 操作：`保存并返回`、`下一步：确认怎么评`。

## 6. 第二步：确认怎么评

### 6.1 目的

在修改前约定怎样判断改善，避免系统自行改变成功标准。

系统根据材料生成可编辑建议，不要求用户从零搭建评价体系。

### 6.2 学员点评的默认建议

| 检查方面 | 回答的问题 |
|---|---|
| 专家问题修复 | 错误归因、遗漏、扣分不当等原问题是否解决 |
| 原有能力保持 | 原来正确的判断有没有退步 |
| 整体业务质量 | 评分、点评依据和修改建议是否符合要求 |

明确区分希望改善的指标、不能违反的要求、仅供观察的指标。严重约束不能由其他高分抵消。

### 6.3 专家意见整理为检查项

保留专家原话，并生成待确认的结构化内容：

- 问题描述及适用条件。
- 对应案例和输出证据。
- 期望表现。
- 检查方式。
- 影响程度。
- 状态：已确认错误、偏好建议或待核实问题。

例如“学员只是计算错了，AI 却说概念不清且扣分过重”，应拆分为错误归因和扣分两项检查，分别提供证据和判定方式。

### 6.4 标签、备注与评级

| 内容 | 职责 |
|---|---|
| 标签 | 归纳具体表现，允许一条结果多个标签 |
| 备注 | 保留依据、解释及期望，支持整条和选中文字备注 |
| 评级 | 表达整体判断，规则可自定义 |

标签支持创建、定义、停用和同义合并；保留历史记录及合并关系。标签描述现象，不自动等同于原因。

备注原文不可被系统摘要覆盖。

评级支持自定义名称、解释、顺序和改善/持平/退步映射；不默认将字母转为等距数字求平均。规则修改产生新版本，历史评价不被重新解释。

### 6.5 ABCD 的首个支持方案

| 评级 | 用户含义 | 展示依据 |
|---|---|---|
| A | 原错误全部避免 | 逐项解决情况及新增问题检查 |
| B | 部分避免 | 已解决和仍存在的具体问题 |
| C | 没有避免 | 原问题仍然存在的证据 |
| D | 出现更多问题或明显退步 | 新增、回退问题及影响 |

需额外确认“修复原问题但出现新问题”的评级规则。建议严重新增问题优先判为 D；一般问题的取舍由项目定义。始终同时展示原问题改善与新增问题两个维度，不能只展示一个字母。

“无法判断”和“尚未评价”单独记录。不能用问题数量代替严重程度判断。

### 6.6 检查评价方式是否合理

提供“试评一个案例”，展示判定和依据，允许专家确认或纠正。

程序能判定的用规则，有标准答案的对照答案，需要语义理解的使用自动判定并接受专家核对。单个试评用于理解与调试，不等于自动评价器已经可靠；用于调整评价方式的材料和用于独立检查其可靠性的材料需要区分。

评价结果标明人工、自动、人工确认或人工修正来源，不互相静默覆盖。

### 6.7 运行摘要

开始前展示：模型、优先目标、不能退步的要求、材料用途、运行上限、停止条件及需要人工介入的情况。

金额估算须有可用价格依据；否则展示调用或 Token 上限。演示模式与真实调用明显区分。

操作：`返回材料`、`保存并返回`、`开始原始测评`。

## 7. 第三步：查看原始测评

### 7.1 目的

建立优化起点，确认系统发现的问题确实是用户希望解决的问题。

### 7.2 执行与历史输出

系统按照确认的方案测评原始提示词。导入的历史输出，只有在来源和配置满足比较要求时才能直接用于正式前后对照；否则用于诊断，必要时重新生成可比的原始输出。

### 7.3 页面内容

先展示主要问题，再提供具体案例入口。案例中并列呈现输入、原输出、学员得分、专家意见、自动判定和证据。

用户可以修改问题、添加标签和备注，确认本次优先处理内容。

不强制重新评价全部案例：已有确认数据可复用，自动评价重点提交不确定、有分歧和影响较大的案例供核对。

### 7.4 完成结果

- 原始测评报告。
- 有证据的问题清单。
- 本次优先处理的问题与保留要求。

首次或评价标准未稳定时，主操作为`按这些问题开始自动优化`。后续规则稳定的运行，可预先选择原始测评后自动继续。

## 8. 第四步：自动优化

### 8.1 目的

围绕实际问题重复修改和测评，让系统承担主要执行工作。

```text
查看失败案例 → 提出修改假设 → 修改提示词 → 重新执行任务
      ↑                                      ↓
决定继续或停止 ← 比较并保留版本 ← 检查原问题、新问题及原有能力
```

### 8.2 优化器必须收到的信息

- 当前提示词及可修改、不可修改范围。
- 任务目标与评价标准。
- 实际输入、实际输出。
- 专家问题、标签、备注和证据。
- 原来正确的行为与代表案例。
- 历史修改和测评结果。

不得仅发送一个等级、案例编号或低分维度，要求模型凭空改进。

### 8.3 每轮交付

| 内容 | 说明 |
|---|---|
| 问题证据 | 本轮为什么改 |
| 修改假设 | 预计解决什么，可能原因是什么 |
| 提示词差异 | 实际修改内容 |
| 测评变化 | 哪些改善、持平、退步或无法判断 |
| 保留决定 | 保留或淘汰及依据 |
| 后续方向 | 下一轮尝试什么 |

归因是待验证假设。资料不足、评价错误、运行故障或模型能力限制，不应被强行解释为提示词缺陷。

### 8.4 用户看到的运行页

```text
正在优化：第 3 轮

这轮处理什么
列式正确、计算错误时，原提示词容易归因为概念不清。

准备怎样改
分别判断思路、列式和计算，再给出点评。

正在检查
原问题是否减少；其他判断是否退步；评分是否仍符合标准。

[查看本轮修改] [查看测评结果] [返回项目列表] [停止优化]
```

显示真实阶段、已完成数量及用量；未知总轮数时不展示虚假完成百分比。日志、哈希及请求详情默认折叠。

### 8.5 自动运行与人工参与

- 默认在已确认的方案和上限内连续执行，不要求每轮点击继续。
- 可选择人工参与模式：每轮完成后等待指定评价，再继续。
- 自动模式重点对关键分歧、严重问题或缺失材料请求人工处理。
- 新反馈从后续轮次使用；修改评价规则时保留版本，必要时重评后再比较。
- 达到目标、连续无值得保留的改善、达到上限、主动停止或无法继续的错误，均形成明确停止原因。
- 离开页面不取消运行；本地服务保持运行时后台继续。
- 停止或失败保留已完成输出，重试需避免重复提交和重复计费。

### 8.6 防止越改越差

- 比较主要目标、底线和代价，不只比较平均分。
- 原来合格的案例也要复测。
- 必要时保留各有优势的候选，按明确偏好选择待验证版本。
- 不可修改部分进行实际校验。
- 记录提示词长度变化，设置适用的长度上限。
- 改写失败明确报告，不得静默追加固定业务文本作为成功结果。

## 9. 第五步：验证与使用

### 9.1 目的

检查修改是否不仅修好了已经看过的案例，还能适用于未参与优化的新情况。

固定待验证候选、评价规则和模型配置后，对原始版与候选版进行可比测试。不用最终验证集反复选择候选后仍声称独立验证。

### 9.2 报告顺序

1. 结论：改善、存在退步、未见明显提升或证据不足。
2. 专家原问题的解决情况。
3. 新增问题和原有能力退步情况。
4. 独立验证结果。
5. 代表性案例与详细统计。
6. 完整提示词、修改差异和使用操作。

优化样例与独立验证结果分别展示。人工和自动评价分别统计，明确样本数量、来源、未评、失败和无法判断数量。

新案例没有预先列出的原错误时，按项目通用质量标准评价，不强行套用原问题解决率。

### 9.3 统计口径

| 层次 | 统计内容 |
|---|---|
| 问题项 | 完全解决、部分解决、未解决、无法判断 |
| 案例 | ABCD 分布、合格情况、新增问题、原有正确案例退步 |
| 业务指标 | 评分偏差、错误归因、内容覆盖等任务相关指标 |
| 证据范围 | 优化样例与独立样例、数据来源、评价方式和不确定性 |

多问题案例的“问题项数量”和“案例数量”不能混用。多标签占比可能超过 100%，需要说明。

只给新结果打标签时，不能据此推断原问题减少了多少。比较同一指标必须具有可比较的前后记录。

不设通用的固定样本数作为有效保证；根据数据规模、来源关系及差异给出相称结论。对波动较大的任务进行合理重复，重复输出不能当作新的独立来源。

### 9.4 使用和继续优化

提供`复制提示词`、`导出报告`、`设为试用版本`、`保留原版本`。正式采用遵守项目的验证要求，复制文本不等于验证通过。

没有独立样例时明确标记“尚未独立验证”。最终验证反馈一旦用于继续改写，该批材料不再作为下一轮的独立证明，需要补充新的验证材料。

## 10. 泛化方式：统一流程，组合评价能力

用户回答“你有什么材料可以判断结果好坏”，系统建议方法。

| 用户材料 | 系统采用的方法 |
|---|---|
| 正确答案、专家分数或合理区间 | 对照答案、计算偏差 |
| 专家指出的问题 | 原问题回归与新增问题检查 |
| 明确业务要求 | 规则或语义检查 |
| 两个结果之间的偏好 | 成对比较 |
| 可执行测试或可观察结果 | 执行验证 |

同一项目可组合多种方式。专家反馈流程为首个完整实现，其他能力逐步接入；不要求用户先学习全部评价方法。

自动判定也要核对其可靠性，重点关注漏判错误、误报问题、不同问题类型的表现和无法判断比例，不能只看总体一致率。专家存在分歧时，保留分歧并澄清标准。

## 11. 复盘与经验积累

复盘不仅研究失败，也研究成功、取舍和不确定性。

每条记录包括：

- 观察到什么。
- 来自哪些样例、评价与备注。
- 本次修改及原因假设。
- 测评是否支持该修改。
- 副作用与反例。
- 适用范围。
- 状态：待验证、当前任务内获得支持、发现反例、已停用。

例如：

> 在具备作答过程的案例中，分别判断思路、列式和计算，有助于减少错误归因；是否导致表达冗长需要同时检查。

不能将局部经验保存成“所有任务都应该这样做”。跨任务复用只提供建议，需要重新验证。

复盘可能导向修改提示词、补资料、改评价标准、修判定者、补案例或放弃修改，不是一律追加提示词规则。

## 12. 返回、保存与异常恢复

| 场景 | 必须达到的行为 |
|---|---|
| 创建中退出 | 保存草稿，项目列表可继续 |
| 编辑和评价 | 显示保存中、已保存或保存失败，保留输入 |
| 查看运行 | 独立地址，刷新后仍是对应运行 |
| 返回列表 | 保留搜索、筛选及位置 |
| 离开运行页 | 不自动停止后台运行 |
| 主动停止 | 保留已完成结果，说明在途处理状态 |
| 网络或调用失败 | 展示失败位置、保留数据、提供可用重试 |
| 本地服务停止 | 明确运行中断，不承诺服务关闭后继续执行 |
| 旧项目或记录不可用 | 展示原因及返回入口，不留空白 |

统一使用明确的上级地址作为返回入口，兼容直接打开详情的情况；同时正确支持浏览器前进、后退。运行、版本和报告都具备可恢复路由。

## 13. 现有项目的工程改造范围

当前实现中，改写器主要接收案例编号与低分维度，缺少完整输入、输出和专家说明，并存在固定点评类兜底片段；候选生成和选择仍是简化流程。界面调整必须与这些能力一起改造。

| 模块 | 改造要求 |
|---|---|
| 任务定义 | 解除四种场景限制，支持自定义输入、输出、目标 |
| 材料准备 | 自动识别、用途确认、导入预览、来源记录 |
| 评价数据 | 自定义评级、标签、备注、证据及规则版本 |
| 评价执行 | 组合检查方法，保留逐项结果与来源 |
| 优化器 | 完整反馈输入、针对性修改、冻结校验、长度控制 |
| 运行编排 | 串联五步，支持真实迭代、停止、人工介入与恢复 |
| 候选选择 | 明确目标、底线及取舍，保存保留和淘汰依据 |
| 结果验证 | 可比前后测评、独立验证、准确统计口径 |
| 前端 | 连续流程、阶段说明、评价对比、独立路由及保存恢复 |
| 历史兼容 | 保留旧任务、配置、输出和报告，新配置不覆盖旧结果 |

主要涉及现有 `web/app.js`、`web/style.css`、`prompt_lib/core.py`、`domain.py`、`engine.py`、`runs.py`，并需要配套调整 API 和存储结构。

保留已有数据隔离、版本快照、预算账本、停止运行、验证及回滚能力，并在新流程中重新验证。不能仅凭功能或表存在，就认定新流程已经完成。

若接入真实 GEPA，将其作为明确的引擎实施和验收项；不得仅改界面名称宣称已实现完整 GEPA 能力。

## 14. 分阶段交付

### 第一阶段：让用户现有流程完整可用

交付项目、材料导入、专家问题整理、自定义标签备注和 ABCD、原始测评、自动修改与复测、结果报告、返回及恢复。

验收：用户用现有真实材料完成一次优化，能看懂每一步；能追溯一条专家意见如何影响修改及测评。第一阶段即如实区分本批案例改善与独立验证，不延后数据真实性要求。

### 第二阶段：让效果证据充分可靠

交付自动判定核对、新问题与回退检查、完整独立验证、统计口径及改进记录。

验收：系统能够解释为什么认为有效，也能正确报告无提升、退步和证据不足，不以运行完成代替优化成功。

### 第三阶段：扩展通用任务能力

交付更多评价方式、数据自动识别增强、候选取舍及跨任务经验建议。

验收：非教学任务无需套用固定业务模板，操作主线不变；界面声明与实际引擎能力一致。

## 15. 最终验收标准

### 15.1 用户理解与操作

让未参与设计的人拿着提示词和案例，在不依赖口头指导的情况下使用，并确认其能回答：

1. 我现在在哪一步？
2. 这一步为什么必要？
3. 我需要做什么？
4. 系统正在替我做什么？
5. 为什么这次修改值得保留？
6. 结论来自哪些案例和评价？
7. 我离开后，如何回来继续？

### 15.2 业务与工程

- 专家意见、检查项、改动和测评之间可以完整追溯。
- 原问题修复、新问题、原有能力退步分别可见。
- ABCD 自定义规则实际生效，并正确处理无法判断和规则版本。
- 正确区分学员得分和点评质量评价。
- 原始与候选比较条件明确，缺失、失败和样本范围可见。
- 评价专用信息不被误发给执行模型。
- 不可修改内容不会在候选中被改写。
- 演示结果不会被呈现为真实效果证据。
- 独立验证材料不用于反复挑选候选或指导修改后仍当作独立证明。
- 浏览器返回、刷新、草稿恢复、运行恢复和停止行为符合说明。
- 保留已有历史数据和关键业务约束，新增测试覆盖这些真实风险。

最终交付是一次完整、可理解、可追溯的自动优化：用户沿五步前进，系统完成测评与迭代，最后同时交付提示词和效果证据。

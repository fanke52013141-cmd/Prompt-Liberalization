## 二、分级问题清单

### Blocker（阻断任务完成，必须修）

#### B1 · 移动端主导航丢失 4/6 项，无任何溢出提示

- **位置**：`prompt-lab/static/style.css:39` `.nav { display:flex; gap:4px; overflow-x:auto; }`
- **现象**：390px 视口下，导航容器实际宽 186px，而 6 个导航项总宽 472px。截图 `lab-m1-home` 只能看到「我的提示词 / 新建优化」，「用一用 / 考个试 / 花费与记录 / 设置」**完全不可见**。
- **用户场景**：用户在手机上完成「用一用 → 反馈回流 → 攒例子 → 考个试」这条最自然的闭环，但「用一用」入口根本找不到。
- **影响**：功能可达性归零；`overflow-x:auto` 会渲染细滚动条，桌面端几乎不可见，移动端用户不会知道右侧还有内容，也不会想到横向滑动。这是典型的"能实现但用户不知道"的设计。
- **根因**：桌面优先的固定 `flex` 导航 + 品牌区 `white-space:nowrap` 抢占空间，未设移动端断点。
- **推荐改法**：≤ 768px 时把导航改为**底部固定 Tab 栏**（6 项正好适配移动端底部拇指区），品牌区压缩为单行标题；或退化为汉堡菜单 + 抽屉。移动端不应保留横向滚动导航。

```css
/* 建议：移动端底部导航 */
@media (max-width: 768px) {
  .topbar-inner { height: 52px; padding: 0 14px; }
  .nav {
    position: fixed; left: 0; right: 0; bottom: 0;
    display: grid; grid-template-columns: repeat(6, 1fr);
    overflow: visible; background: var(--card);
    border-top: 1px solid var(--line); padding: 6px 0;
    padding-bottom: calc(6px + env(safe-area-inset-bottom));
  }
  .nav a { padding: 6px 2px; font-size: 11px; text-align: center; }
  .main { padding-bottom: 88px; }
}
```

#### B2 · 盲评对比页左右栏错位，破坏对比基准

- **位置**：`prompt-lab/static/app.js:451-484` `drawPair()` / `paneHtml()`
- **现象**：截图 `core-04-compare` 显示，甲栏内容较长、乙栏较短，两栏**高度不等**。乙的「能直接用吗？」区块浮到了页面中部，与甲的评级区不在同一水平基线上；下方「整体哪份更好」卡片也随之错位。
- **用户场景**：这是整个产品的核心决策页面——用户必须**左右扫视同一位置做对比**。基线不齐会让人反复上下找对应元素，直接增加误判概率。
- **影响**：盲评的"匿名 + 对称"是统计有效性的前提（右侧 `.opt` 的甲/乙实际对应随机的新旧版本）。视觉不对称会不自觉地暗示长度更长/更短的一侧更优，污染判断。
- **根因**：`.compare-grid` 只做了 `grid-template-columns: 1fr 1fr`，未对 `.pane` 做等高对齐；内容长度天然不可控。
- **推荐改法**：
  1. `.pane { display:flex; flex-direction:column; }` + 给输出框 `flex:1`，使两栏评级区底部对齐；
  2. 输出框统一固定高度（建议 `min-height: 220px; max-height: 260px`）并内部滚动，让"输出区/评级区"形成稳定的两行结构；
  3. 更进一步：把"能直接用吗"评级区**移出两栏**，改为在栏下并排两组选项并显式标注"甲/乙"，彻底消除对齐依赖。

```css
.compare-grid { display: grid; grid-template-columns: 1fr 1fr; gap: 14px; align-items: stretch; }
.pane { display: flex; flex-direction: column; }
.pane .output-box { flex: 1; max-height: 260px; }
```

#### B3 · 轻量版未配置 AI 接口时，主流程无法启动但入口不隐蔽

- **位置**：`prompt-lab/static/app.js:129`（首页 banner）、`:192`（新建优化提交按钮）
- **现象**：`/api/state` 返回 `configured:false` 时，首页仅显示一条浅蓝 banner 提示去设置。用户仍可点「＋ 新建优化」并走完 4 步表单，直到点「创建并开始」才会在第 1 次调用时报错。
- **用户场景**：新用户按提示词贴完、贴完例子、提交 → 才发现需要先去设置页配密钥，前面的努力全部作废，需回首页再走一遍。
- **影响**：首次使用流失点。这与"降低使用门槛"的设计目标直接冲突。
- **推荐改法**：采用**渐进式披露 (Progressive Disclosure)**——未配置时，把「新建优化」替换为单个引导按钮「① 先填 AI 接口（约 1 分钟）」，配置完成后再展示完整流程；或在表单顶部插入可折叠的步骤 0 提示条，"未配置"时默认展开。

### Warning（影响体验，建议本轮修）

#### W0 · 浏览器刷新/关页面时向用户控制台抛整段 traceback（已修复）

> **状态**：评审期间实际触发（服务在我评审结束约 15 小时后退出时暴露），已定位根因并修复，37 项端到端测试零回归。

- **位置**：`prompt-lab/server.py:2053-2060` `_dispatch()` 的兜底 `except`
- **现象**：用户在生成过程中刷新或关掉标签页 → socket 写响应抛 `ConnectionResetError` → 兜底 `except Exception` 又尝试写一次 500 响应 → 第二次写再次失败，异常冒泡到 `socketserver`，把整段Python traceback 打进用户可见的黑色控制台窗口。
- **用户场景**：用户只是关了个页面，屏幕上却出现十几行英文报错，第一反应是"我是不是弄坏了"。
- **影响**：把**正常操作**（关页面）呈现为**程序崩溃**；用户对工具可靠性信任度直接受损。这也是唯一一处会让服务进程最终退出的路径。
- **根因**：兜底 `except` 里没有区分"业务异常"与"客户端已断开"；响应写出动作本身缺少断连保护。
- **已实施方案**：
  1. 新增 `ClientGone` 异常类型，在 `_dispatch` 中单独捕获并静默 `return`；
  2. 新增 `Handler._try_json()` 包裹响应写出，捕获 `ConnectionResetError / BrokenPipeError / ConnectionAbortedError / OSError` 后静默收尾；
  3. `ApiError` 与兜底分支统一改走 `_try_json`，避免二次写失败。
- **验证**：`.ux-audit/repro_reset.py` 用 `SO_LINGER=0` 发 RST 模拟粗暴断开，修复前稳定复现 traceback，修复后输出干净且服务存活。

#### W1 · 原生弹窗与自定义弹窗混用，体验割裂

- **位置**：`prompt-lab/static/app.js:295, 577, 587, 691, 828`
- **现象**：轻量版 5 处使用原生 `window.confirm/prompt`；主版本已全面实现自定义 `uiConfirm()`（含 `role="dialog" aria-modal="true"`、Esc 关闭、焦点管理、语气图标）。
- **影响**：原生弹窗样式不可控、与品牌视觉不符、Esc 行为在部分弹窗不生效；`window.prompt("把这轮优化的上限提高到多少？")` 输入的是**金额/次数这类关键参数**，原生弹窗无单位说明、无输入校验反馈、无「取消/确认」按钮文案定制。
- **推荐改法**：把主版本的 `uiConfirm()` 提取为共享模块；`raiseCapAndResume` 改用带输入框的专用弹窗（复用 `prompt-lab` 现有弹层样式），补齐「取消 / 提高上限并继续」按钮与单位后缀「元」。

#### W2 · 提示词详情页「优化记录」区标题与内容脱节

- **位置**：`prompt-lab/static/app.js:609-625`
- **现象**：截图 `core-05` 显示 h2「优化记录」下方直接是运行卡片，卡片内只有「考试 / 已完成 / 时间 / 打开」，**没有说明这次运行的性质、用了几个例子、花了多少、结论是什么**（结论仅一行 headline）。
- **影响**：用户无法在不点开的情况下判断"上次那次考试到底考了什么"，多轮历史后回溯成本高。
- **推荐改法**：运行卡片补充 `4 个元信息 chip`：例子数、用例版本对比（如 v2 vs v3）、调用次数/花费、结论标签（转正/仅参考/未提升）。

#### W3 · 版本历史「操作」列全是裸文字链接，破坏层级与可发现性

- **位置**：`prompt-lab/static/app.js:666-677`
- **现象**：表格操作列为「查看 设为正式 回滚到此版」三个并列蓝色文字链接，无按钮形态、无主次区分、无危险操作区分。截图中 v2 行（当前正式版）与 v1/v3 行的操作完全同构。
- **影响**：「设为正式」是**高影响不可逆操作**（会改指针），却与只读的「查看」视觉等权；且「回滚」只在非当前正式版出现，需读代码才能知道规律。
- **推荐改法**：改为按钮组：`查看`（ghost 小按钮）｜`设为正式`（当前正式版行显示 `当前版本` 禁用徽标，其余显示 ghost）｜`回滚到此版`（warn 色）。危险操作统一走确认弹窗并说明影响。

#### W4 · 「设置」页破坏 Task 序列：测试连接与保存割裂

- **位置**：`prompt-lab/static/app.js:890-966`
- **现象**：截图 `lab-06-settings` 显示，AI 接口卡片底部只有「测试连接」按钮，「保存设置」按钮被孤立在最底部（在花费上限卡片之外）。用户配好地址/密钥/模型后，最自然的动作是「保存」，但视觉焦点在「测试连接」。
- **影响**：形成"测试通过 → 忘记保存 → 重启后配置丢失"的真实风险；同时用户可能误以为「测试连接」已经保存了配置（它只传入表单值、不落库）。
- **推荐改法**：把「测试连接」改为**内联校验**（失焦即测，在字段旁显示 ✓/✗ 与延迟），主按钮统一为「保存设置」。若保留测试按钮，放在保存按钮旁并明确标注「仅测试，不保存」。

#### W5 · 新建优化表单超长（>1000px）且无分组锚点

- **位置**：`prompt-lab/static/app.js:178-195`
- **现象**：截图 `lab-02-new` 显示单页承载 3 个例子 × 2 个 textarea（输入 + 参考材料），加上提示词 textarea，整页约 1000px，用户需长距离滚动。
- **影响**：滚动到第 3 个例子时，"创建并开始"按钮已远离视野；用户容易漏填第 3 个例子。
- **推荐改法**：① 例子默认只展开 2 个（已实现），但把"参考材料"改为 `<details>` 折叠（次要信息降级）；② 底部主按钮改为 `position: sticky; bottom: 12px` 常驻，或改为**分步向导**（文案已承诺"四步"，但当前 UI 是一页到底——承诺与实现不符，这是文案与体验的**一致性缺陷**）。

#### W6 · 主版本首页把「新建项目」表单直接内联在项目列表下方

- **位置**：`web/app.js:186` `pageProjects()`
- **现象**：截图 `main-01` 显示项目列表下方直接跟了一个约 470px 高的完整表单（含输入字段/评价专用字段/优化目标三组），需滚动才能看到底部的「创建项目」。
- **影响**：项目列表这一页承担了两个不同任务（浏览 + 新建），违反"一屏一任务"；且新建表单的字段表格式布局对新用户认知负担高。
- **推荐改法**：项目列表只保留卡片 + 一个醒目的「＋ 新建项目」按钮，点击后以**模态框或独立页**承载表单；创建成功后返回列表。

## 三、设计系统评估

### 3.1 现状评分

| 维度 | 评分 | 依据 |
|---|---|---|
| 一致性 | ★★★☆☆ | 单套系统内 Token 化程度高（主版 20 个 Token 驱动全部组件）；但跨两套系统不统一 |
| 层次与可扫读性 | ★★★★☆ | 主版值主张三列、流程 chips、stat-hero、action-bar 吸底条层次清晰；轻量版偏平 |
| 反馈与状态完备 | ★★★★☆ | 运行态覆盖完整（10 种状态标签）、失败态有专门文案、`banner warn`/`empty` 齐备 |
| 空/错误状态 | ★★★★☆ | 空状态有引导文案且带下一步动作；错误有 `esc()` 转义 + 兜底提示 |
| 键盘可达 | ★★★★☆ | 30 次 Tab 全程焦点环可见；`uiConfirm` 有 Esc + focus 管理 |
| 阅读对比度 | ★★★☆☆ | 正文 AAA，但 `--faint` 2.67:1 不达标，轻量版 4 处 AA 以下 |
| 移动端适配 | ★★☆☆☆ | 轻量版导航 Blocker；主版 216px 固定侧栏无任何断点，390px 下会挤压内容 |

## 四、核心流程体验评估（轻量版 4 步主线）

对照 README 承诺的「新建优化 → 用一用 → 考个试」闭环：

| 阶段 | 做得好的地方 | 问题 | 级别 |
|---|---|---|---|
| **新建优化** | 文案口语化（"原样贴进来，不用整理"）；明确告知花费区间（"几毛到几块钱"）；例子下限校验（< 2 份拦截） | 单页过长；承诺"四步"但 UI 是一页到底；未配置接口不阻断 | W5 / B3 |
| **原始测评** | 逐份判断"能直接用吗"是低认知负荷问法；失败条目单独说明"不影响其他条"；自动汇总问题为改进方向（`prefill` 拼接） | 失败条目无重试入口；`options` 可点但**无键盘/方向键支持** | S / Suggestion |
| **盲评对比** | 左右打乱匿名、两边都评完才揭晓、揭晓用中性色 `.reveal`——**方法论设计优秀** | 左右栏不等高（B2）；选项无 radiogroup 语义 | **Blocker** |
| **结论页** | `sample_warning` + `warn-line` + "只能当参考"的诚实表述；逐份列出"新版弄坏的/修好的"可下钻证据——**证据链完整，是本产品最强部分** | 「新版弄坏的（原来是能直接用的）」标题括号解释冗长；`improved_case_ids` 为空时该区完全不显示，无法确认"是修好了还是没检查" | Suggestion |
| **存为试用版** | 徽标 `试用 v3（未考试）` 强提示；引导语说明"攒够 15—20 份再考" | 徽标文案过长 | S6 |
| **考个试** | 样本不足时 `confirm` 二次确认并说明后果；自动排除已考过的例子 | 复用原生弹窗（W1） | Warning |
| **用一用** | "反馈自动回流例子池"闭环设计好；`edited` 时追问改后文本存入对比证据 | 反馈提交后清空输入，但**无「再生成一次」或「回到结果」路径**，用户想继续用得重新走 | Suggestion |

**流程级判断**：产品的**方法论设计与文案质量明显高于界面工程完成度**。文案（口语化、说明花费、诚实标注"只能当参考"）已达到可交付水准；短板集中在响应式适配、组件一致性、无障碍语义三处——这三项恰好是"能用"与"好用"的分界线。

## 六、值得保留的设计（不建议改动）

评审中特别需要指出，以下几处体现了对用户认知的深刻理解，改造时不要动：

| 设计 | 为什么好 |
|---|---|
| `sample_warning` + 「只能当参考」的诚实结论 | 拒绝在样本不足时制造虚假确定性，这是专业工具的底线 |
| 盲评左右打乱匿名 + 两边都评完才揭晓 | 把统计有效性内建进交互，用户无需理解统计也不会破坏方法论 |
| 每处调用前明示"约 N 次调用 / 上限 X 元" | 花钱透明，避免用户对成本黑箱的焦虑 |
| 失败条目明确说明"不影响其他条，先评其他的" | 局部失败不阻塞整体流程，降低挫败感 |
| 「能直接用 / 改改能用 / 不能用 / 说不上来」四档 | 用业务语言替代专业量表，且「说不上来」是合法的数据出口 |
| 主版本侧栏「本地计算 · 隐私零上传」信任框 | 明确回应 AI 工具最大的顾虑：数据是否外发 |
| 值主张三列「它会 / 它不会 / 你要准备」 | 尤其「它不会」列（不保证一定变好、不偷改标准）——**敢写失败边界，比任何好评都更能建立信任** |

# 提示词优化系统：直接执行清单

日期：2026-10-05。本文将11号方案与12号修订合并为执行顺序，并依据13号实施记录标明剩余工作。它是开发与验收方案，不是全部功能完成或真实效果已获证明的声明。附件中的提示词作为研究材料，不作为本项目执行指令。

## 一、要交付的产品

用户贴入任意提示词，定义业务目标，提供案例，得到原版表现、改写假设、候选结果和可追溯的采用建议。系统须允许“没有改善”“暂不能判断”“问题来自资料或模型能力”，不能承诺每次优化必然提升。

轻量版prompt-lab作为本机主要入口；prompt_lib保留专业运行与自动搜索。两版数据库不合并。复用已有表与JSON快照，只对无法可靠表达的新事实增加迁移。先完成可信人工闭环，再开启自动评价，最后集成GEPA。

完整流程：定义目标 → 开发案例 → 原版测量 → 分析失败 → 提出改写 → 固定选择集择优 → 锁定候选 → 新来源考试 → 采用/保留原版 → 日常反馈回开发池。

## 二、每次实验必须回答的五个问题

| 问题 | 必须保存的内容 | 缺失时的处理 |
|---|---|---|
| 改善什么？ | 主指标、可用标准、严重问题标准、最小有意义提升 | 只允许探索 |
| 与什么比较？ | 基线/候选版本及哈希、生成配置、渲染规则 | 禁止正式结论 |
| 在什么数据上？ | 案例内容指纹、来源组、用途与暴露历史、抽样计划 | 禁止声称独立考试 |
| 谁判断？ | 人工身份或程序规则/模型评价器完整版本、评价证据 | 无法判断保留unknown |
| 花了多少？ | 每次物理请求、预留、实际用量或费用未知、人工耗时 | 不显示为零成本 |

内容任务可优先使用直接可用率；分类任务明确macro/micro F1与重点类别，精确答案用exact match。格式合规、严重问题、成本、耗时是并列约束。禁止把几个任意权重的分数合成一个“万能优化率”。

直接可用率的分母包含所有计划案例，生成失败或截断不得从分母删除。评价无法判断单列unknown，并显示改善的上下界。来源相关的多个案例不能当多个独立样本。alpha、提升门槛、数量等事前冻结；15条、5个百分点、85%一致率都不是通用合格线。

## 四、按顺序执行的开发工作包

每个工作包交付代码、必要迁移、对应测试、使用说明及实施记录。完成一个可审查行为再领取下一个；以下文件名是改动定位，新增API与结构须按现有代码落实。

### A1：锁定实验数据，阻断新旧数据混比（P1）

改动：prompt_lib/runs.py、domain.py、engine.py及GEPA应用桥接。

1. 创建运行时从服务端读取dev/select案例，保存案例ID、预期用途、来源组及输入/参考内容哈希；拒绝客户端伪造绑定。
2. 案例绑定写入实验快照，参与snapshot_hash；不把参考答案复制到公开生成请求或优化器选择集消息。
3. 启动、恢复、每个阶段和每个案例执行前核对绑定。内容、参考、来源或用途改变则停止并提示新建实验。
4. 不用旧基线成绩与修改后的候选数据计算提升。历史缺绑定运行保留查看，不补造可信快照。

验收：完成基线后暂停，分别修改输入、参考、来源、split，恢复均在新模型请求前拒绝；账本请求数不增加；未修改时复用原输出正常继续。

### A2：将正式考试改成持久任务（P1）

改动：主版本AcceptanceService、DataService、runs.py、DB迁移及验收API。

1. 创建考试job，绑定候选、协议、模型配置和成员列表，与来源占用同事务提交。
2. 状态按bound→generating→rating→report_ready→completed推进，预算暂停与进程中断保留原job。
3. 每个案例×版本×重复编号具有稳定logical_id；成功响应/输出复用，未确认外部请求进入人工核对。
4. 报告写入幂等；同候选、协议、样本清单重复提交返回同任务。取消也保留暴露历史。
5. 整批盲评完成前不返回版本身份，提交后评分锁定。更正追加修订报告，旧报告不继续授权采用。

验收：绑定后、第三条输出后、报告保存前分别终止测试进程，重启继续；不重复成功调用、报告或样本计数；其他候选不能复用已暴露考题。

### A3：未知请求人工核对与费用说明（P1）

改动：ledger.py、engine.py、运行API与web/app.js；轻量版对齐同一行为。

1. 展示reserved/sent_unknown/usage_unknown，以及请求时间、角色、接口、请求指纹和预留；不展示密钥。
2. 提供“补录已确认结果/用量”“确认未被受理”“新尝试重发”操作；记录操作者、原因和证据。
3. 缺真实结果不得直接标成功；缺供应商核验不得把未知费用改零。重发创建新attempt并再次预留。
4. Token与金额标明估算口径；每次物理尝试计数。若提供硬次数上限，服务端原子执行，包含重试和反思调用。

验收：重复核对不重复结算；过期revision拒绝；结果未知不自动重发；重发超预算不出站；已成功记录不会被晚到错误擦除。

### A8：真实业务价值验证（交付必需）

1. 选择用户真实重复任务，写清可用标准、严重底线、最小有意义提升与总预算；先以小规模pilot估计难度和分歧比例。

### A9：同一提示词重复正式检验的累计误报控制（已修复）

问题：只要求独立新来源和固定样本，仍允许用户反复启动新考试；如果每轮继续按完整5%阈值判断，挑选最终显著的一次会抬高误报率。

实现：同一提示词所有已创建正式考试共用5%预算，第i次考试阈值为0.05/2^i，所有轮次阈值之和不超过0.05；按SQLite写事务中的服务端记录数决定i，中断也计入。考试协议版本升至2，保存次数、累计预算、校正阈值和方法；结论复核该序号确为此提示词第i次正式考试。UI在创建前显示阈值，基于当前序号估算样本量，计划过期返回409；报告展示预算和当轮阈值。模型/用户无法通过提交更大的alpha覆盖服务端规则。

验收：7个案例全部改善时双侧精确p=0.015625；首轮可以通过0.025，第二轮不能通过0.0125。验证千轮阈值总和不超过5%，另验证过期页面被拒绝、校正协议完整性、客户端不能提高累计预算及协议哈希绑定。当前专项 `tests/test_protocol.py` 与 `prompt-lab/tests/test_confirmatory.py` 10项通过；需再运行官方双版本离线入口、真实浏览器检查和空白/语法检查。该修复按未来预先分配阈值控制同一提示词重复检验，不代表跨提示词选择或历史旧报告获得回溯性错误率保证。

最终回归补充（2026-10-05，计时与报告消耗最新变更后）：仓库统一离线入口通过，主版本339项通过、4项可选GEPA测试跳过；轻量版unittest 35项及E2E 37项通过。A9专项10项、严重金标/审计工作流59项通过；两版相关Chromium路径均通过。A9是轻量版按提示词累计分配；主版本则每项目只允许一次封存考试绑定，已消耗的考题不能为新候选重用。未运行真实付费模型或业务数据实验。
